# Deployment notes — what must change before cut-over

MBD refactor P2.5 (§15.7 of `MBD_REFACTOR_PROMPT.md`). The repo now builds a Spring Boot jar with
Gradle; the WildFly WAR, its Maven build and its Liquibase jar are gone (P2.6). **Nothing below has
been changed in the pipeline or Helm repos yet**: `azure-pipelines.yaml` is left as it was, because
its templates (`hmcts/cpp-azure-devops-templates`) are Maven/WAR-based and must not be guessed at
from here. This is the list of what has to change, for the owners of those repos.

## 1. What the build now produces

| Artefact | How | Where |
|---|---|---|
| Boot fat jar | `./gradlew :listing-api:bootJar` (`-DARTEFACT_VERSION=<v>` sets the version, default `0.0.999`) | `listing-api/build/libs/cpp-context-listing-<version>.jar` (+ a `-plain` jar) |
| Published jar | `./gradlew :listing-api:publish` (GitHub Packages and the HMCTS Azure Artifacts feed, idempotent: an existing version is skipped) | `uk.gov.hmcts.cp:cpp-context-listing` (as courtscheduler) |
| SBOM, build info, git properties | generated by the api build (CycloneDX, `buildInfo`, `gradle-git-properties`) | `listing-api/build/…` |
| Image | repo-root `Dockerfile` (`ARG BASE_IMAGE`, default `eclipse-temurin:25-jre`, CI: `hmcts/apm-services:25-jre`), copies `build/libs/*.jar` and `docker/startup.sh`, runs as non-root `app` | built from the repo root after the jar is placed in `build/libs/` |

Local image check:

    ./gradlew :listing-api:bootJar && mkdir -p build/libs && cp listing-api/build/libs/*.jar build/libs/
    docker build -t listing .

The IT stack builds its own image from the same jar (`listing-integration-test-spring/docker/`).

## 2. Pipeline (`azure-pipelines.yaml`)

Decide first (open, §15.7): stay on ADO with a Gradle-capable template, or move to courtscheduler's
flow (GitHub Actions `ci-build-publish.yml` publishes the jar, then the ADO `cp-gh-artifact-to-acr`
pipeline builds the image from the repo-root `Dockerfile`). Either way, the following no longer hold:

- `pool.demands: identifier -equals ubuntu24-j17` → the build needs **JDK 25** (Gradle toolchain).
- `context-verify.yaml` / `context-validation.yaml` run Maven (`mvn verify`, Sonar from the root
  `pom.xml`, WAR build). Replace with `./gradlew clean build` (unit tests + Spring ITs; needs Docker
  compose v2 on the agent) and, for the full IT gate, `./runIntegrationTests.sh nounit`.
- `sonarqubeProject: uk.gov.moj.cpp.listing:listing-parent` → there is no Maven parent; the Sonar
  key and the coverage/cpd exclusions must be set for the Gradle build.
- `itTest_Folder: listing-integration-test` → the ITs are `listing-integration-test-spring` and
  `listing-integration-test-legacy`, and they no longer need `cpp-developers-docker`/WildFly.
- Artefact publishing: `uk.gov.moj.cpp.listing:listing-service` WAR (+ `listing-viewstore-liquibase`
  jar) → the Boot jar above.
- Feed credentials for the build: `AZURE_DEVOPS_ARTIFACT_USERNAME` / `AZURE_DEVOPS_ARTIFACT_TOKEN`
  (needed for `cp-auth-rules-filter` and `cp-audit-filter-springboot`; the legacy IT module also
  resolves its `uk.gov.*` test jars from that feed when they are not in `~/.m2`).

## 3. Helm / deployment (aks-deploy repo)

- Image: the WildFly image (`docker/Dockerfile_listing-service`, deleted) → the Boot image above.
  Entrypoint `docker/startup.sh` runs `exec java $JAVA_OPTS -jar …`; set heap etc. in `JAVA_OPTS`.
- Context path and port: `/listing-service` (both command and query roots, ADR 008), port
  `SERVER_PORT` (default 8080). The command/query ingress paths stay the same.
- Probes: Actuator `/listing-service/actuator/health/liveness` and `/readiness`; metrics
  `/listing-service/actuator/prometheus`. The WildFly healthchecks are gone.
- Database migrations: Liquibase runs **in the app at startup** (`LISTING_LIQUIBASE_ENABLED`, default
  on). The separate Liquibase job/init container that ran `listing-viewstore-liquibase.jar`
  (`docker/scripts/liquibase.sh`, deleted) must be removed. Only the viewstore database is used;
  the event store, event-buffer and system databases are no longer read or written.
- Configuration: every setting is a `LISTING_*` environment variable (or a file under
  `/mnt/secrets/rpe/` via `configtree`). The WildFly `standalone-listing.xml` system properties and
  JNDI bindings no longer apply. The variables, grouped:
  - datasource: `LISTING_DATASOURCE_URL`, `_USERNAME`, `_PASSWORD`, `_DRIVER`, `LISTING_DB_POOL_SIZE`, `LISTING_DB_MIN_IDLE`;
  - Artemis: `LISTING_ARTEMIS_HOST_PRIMARY`, `_HOST_SECONDARY`, `_HA`, `_PORT`, `_USER`, `_PASSWORD`,
    `_SSL_ENABLED`, `_KEYSTORE`, `_KEYSTORE_PASSWORD`, `_TRUSTSTORE`, `_TRUSTSTORE_PASSWORD`,
    `_VERIFY_HOST`, `_CLIENT_AUTH_REQUIRED`, `LISTING_JMS_*` (reconnect/retry/TTL tuning),
    `LISTING_MESSAGING_ENABLED`, `LISTING_PUBLIC_EVENT_TOPIC`, `_SUBSCRIPTION`, `_CONCURRENCY`,
    `_AUTO_STARTUP`, `LISTING_OUTBOX_RELAY_*`, `LISTING_INBOUND_DEDUP_*`;
  - downstream: `LISTING_BASE_URL`, `LISTING_COURTSCHEDULER_BASE_URL`, `LISTING_HEARING_QUERY_BASE_URL`,
    `LISTING_PROGRESSION_COMMAND_BASE_URL`, `LISTING_HTTP_CONNECT_TIMEOUT_SECONDS`,
    `LISTING_HTTP_READ_TIMEOUT_SECONDS`, `LISTING_SYSTEM_USER_ID`;
  - XHIBIT WebDAV: `LISTING_WEBDAV_OUTBOUND_URL`, `_USER`, `_PASSWORD`, `_CONNECT_TIMEOUT_SECONDS`,
    `_REQUEST_TIMEOUT_SECONDS`;
  - access control and audit: `LISTING_AUTHZ_ENABLED` (**must be true in every real environment**),
    `LISTING_AUDIT_ENABLED`, `LISTING_HTTP_AUDIT_ENABLED`, `LISTING_REST_SPECIFICATION`;
  - other: `LISTING_ENVELOPE_ENABLED`, `LISTING_QUERY_RANGE_SEARCH_MAX_PAGE_SIZE`, `LOG_LEVEL_ROOT`,
    `LOG_LEVEL_LISTING`, `VIRTUAL_THREADS`.
  Check the defaults in `listing-api/src/main/resources/application*.y*ml` before relying on them;
  several are local-development defaults.
- Azure: Managed Identity only; no connection strings, SAS tokens or keys in values (CLAUDE.md).
- Logging: JSON to stdout (`logback.xml`), so the log shipper needs no WildFly `server.log` parsing.

## 4. Broker

- The app reuses the legacy durable shared subscription `listing.event.processor.public.event` on
  `public.event` with the same selector (D15), so the backlog carries over at cut-over.
- The queues/topic the JEE app alone used (`listing.handler.command`, `listing.event` and their
  subscriptions) are no longer consumed; drain and remove them after cut-over.

## 5. Cut-over runbook items still open

- M3 cut-over rehearsal in sandbox (big-bang, D6): stop the WAR, deploy the Boot app on the same
  viewstore, smoke test; rollback = restore the DB snapshot and redeploy the WAR (the WAR must still
  be buildable from git history at commit `b932de14b`; note the Liquibase checksum upgrade in D21).
- No backfill runs at cut-over (D30): aggregate-only state the JEE app kept only in its snapshots is
  not migrated into the Phase 2 rules tables (ADR 015).
- One `SELECT` of `DATABASECHANGELOG` on a production copy to confirm the D21 identity.
- `runSystemCommand.sh` (JMX `CATCHUP` etc.) is retired with no equivalent (§15.8).
